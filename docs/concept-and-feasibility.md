# Continuum：持续服务的概念与技术可行性准备稿

日期：2026-09-21

状态：研究准备草案；实验尚未执行，API、实现语言与产品边界尚未定案。

本稿承接《研究 Cordis 持续服务概念》中的概念综述、管理套件蓝图，以及后来“小运行时内核＋可选生态”的产品讨论。当前目的，是把这些材料收敛为可验证的核心承诺，作为产品化之前的研究入口。

## 1. 本阶段要回答的问题

> 能否用一套足够小、可组合的组件协议，在明确的故障与资源模型下，管理局部失效、合法降级和局部恢复，并让这些保证能被独立验证？

前序讨论中值得保留的定位：

- 持续服务关注影响遏制、部分有效性与局部恢复；动态更新是派生场景。
- 组件需要明确的身份、能力依赖、生命周期、资源及副作用所有权。
- 状态连续性、一致演进、强隔离和分布式协调可以分别增强，须分别声明保证。
- 产品可以围绕嵌入式运行时展开，由适配器、持久管理面和开发工具扩展。

这些是本项目延续的工作方向。“五个原语已经足够”“一定比其他框架简单”“完整套件具有产品价值”仍是待验证假设。

## 2. 概念先收敛到可声明的保证

建议使用以下工作定义：

> 持续服务是一种组合式运行时性质：在声明的故障模型、资源耦合与服务策略下，系统能够把局部扰动的影响限制在约定范围内，持续提供仍然合法的服务模式，并在条件稳定后完成可解释的局部恢复。

其中每个限定都需要落到可检查的对象：

| 对象 | 必须回答的问题 |
|---|---|
| 组件 | 哪个逻辑组件、哪次运行实例、当前属于哪次激活？ |
| 能力绑定 | 消费者实际使用哪个提供者？依赖是必需、可选还是可替代？ |
| 所有权 | 谁负责监听器、任务、连接、状态与外部操作的生命周期？ |
| 服务模式 | 哪些输出属于完整服务、合法降级或明确不可用？ |
| 影响范围 | 哪些依赖、共享资源和恢复组会传播当前扰动？ |
| 恢复证据 | 什么证明资源已释放、旧任务已停止、业务条件已恢复？ |
| 覆盖范围 | 哪些行为受运行时强制管理，哪些只依赖开发者约定？ |

需要分开表示三个维度：组件生命周期、对外服务模式、清理/恢复结果。例如，停止接收新请求可以已经完成，但后台任务仍在排空，外部操作的结果仍待确认。一个 `STOPPED` 状态不足以表达这些情况。

第一轮模型建议限定为有限组件集合、无环依赖、单一明确提供者和已登记资源。可选依赖通过预先声明的服务模式处理。多提供者选择、依赖环、互斥资源与容量优化另外建模；不能无条件假定系统有唯一的“最大有效子图”。

收敛还要求外部条件稳定、调度能取得进展、生命周期操作具有终止或超时处理策略。无限重试和持续抖动不能被计为已恢复。

## 3. 三个协议先于模块拆分

以下是协议需要覆盖的语义，不是已确定的公开 API。

| 协议 | 第一轮必须说明的内容 | 主要歧义 |
|---|---|---|
| Component Contract | 身份、激活代次、能力提供、实际绑定、合法服务模式、恢复组 | 生命周期边界是否与故障边界相同？共享资源由谁拥有？ |
| Effect Contract | 所有者、发生阶段、释放方式、外部可见性、结果证据 | 释放资源、取消执行、补偿业务与撤销历史分别意味着什么？ |
| Transition Contract | 触发条件、接入截止点、排空/取消、完成证据、超时和失败分支 | 什么时候算开始停止？什么时候可以重启？迟到结果如何处理？ |

`scope`、`provide/require`、`effect`、`state`、`transition` 保留为候选概念。是否独立成为原语，应由实验暴露的语义需要决定；业务状态迁移等能力可以先放在适配器中验证。

“自由、简洁、核心更强”也需要转成可比较的目标：同一任务需要多少必填声明、多少专用 API、多少业务代码改动，以及由运行时承担了哪些可验证义务。内核行数少本身不能证明使用成本低。

## 5. 最小验证场景

建议先使用一个具有四个业务组件的宿主：

| 组件 | 关系 | 外部可观察行为 |
|---|---|---|
| source | 提供数据能力；拥有订阅或周期任务 | 发出带唯一编号的数据 |
| processor | 硬依赖 source | 对数据进行确定性处理 |
| enrichment | processor 的可选能力 | 提供附加信息；缺失时 processor 明确进入 basic 模式 |
| independent | 与上述组件无业务依赖 | 持续响应带请求编号的查询 |

外部操作实验另加一个可注入故障的接收端，用来记录已提交的操作。测试控制器在被测宿主之外运行，独立发请求、保存时间线并记录实际结果。

这里的“无业务依赖”只描述逻辑图。如果组件共用事件循环、进程、连接池或其他资源，必须把耦合写进实验条件。

### 实验矩阵

以下实验均未执行。每次执行都要保存版本、配置、事件序列、原始观察与通过/失败结论。

| 编号 | 操作与反例 | 必须观察的结果 | 将决定什么 |
|---|---|---|---|
| E1 依赖有效性 | 移除并恢复 source；另移除 enrichment；重复发送启停命令 | processor 停用或进入约定模式；independent 的实例不被重建且请求满足预设契约；恢复后绑定与模式正确 | 核心是否足以表达局部失活、降级和恢复 |
| E2 生命周期闭合 | 初始化完成部分资源注册后抛错；完成 1,000 次启停；注入清理抛错或挂起 | 可枚举受管资源在成功清理后回到基线；失败/未知资源仍有所有者和记录；没有重复消费者或静默残留 | effect 所有权、清理顺序和失败状态是否足够 |
| E3 并发与迟到作用 | 激活、撤销、恢复交错；停止后完成旧异步任务；消费者保留旧能力引用 | 管理入口拒绝过时代次的新操作；在途操作按声明排空、取消或报告未知；旧完成事件不能覆盖新状态 | 代次、句柄撤销与调用接入控制是否需要进入核心 |
| E4 故障域 | 分别注入回调异常、永久等待、事件循环阻塞、子进程退出；比较同进程与隔离适配器 | 外部观察器记录实际失效范围和恢复时间，并与事先声明的故障域对照 | 哪些保证依赖运行时纪律，哪些依赖保护域和资源隔离 |
| E5 外部结果不确定 | 接收端提交操作后丢弃响应；随后中断执行器并重启 | 稳定操作 ID；结果保持 unknown/pending 直至获得证据；接收端支持去重时不重复提交；不支持时进入明确的对账/人工分支 | Effect Contract 与持久记录的最小要求 |
| E6 管理面可选性 | 基础运行时不连接持久控制面；添加适配器后中断其连接 | 在已声明的离线策略内，已有合法服务继续运行；恢复后对账；禁止把无法持久记录的新外部操作虚报为可恢复 | 数据库管理能力能否作为可选扩展 |

E1—E3 是首轮重点，先建立概念的核心证据。E4 用来校准隔离声明；E5—E6 是扩大产品承诺之前的后续验证。

1,000 次是初始耐久性测试预算，不能证明永久无泄漏。超时与延迟阈值应在运行前按测试环境确定并记录，不能看到结果后调整通过标准。

### 实验必须有独立判据

- 影响预测使用扰动前冻结的声明、实际绑定、资源关系和故障模型，不能事后根据失败日志倒推“预测”。
- 实际影响同时读取外部请求结果、组件实例身份与可枚举资源；运行时自身报告 `healthy` 不构成充分证据。
- 在无故障、手工生命周期管理基线与候选协议实现之间比较结果。记录漏报影响和多报影响，不能只追求一个数字上的命中率。
- 对已知依赖图枚举短事件序列，再加入可复现种子的扰动序列。失败时保留最小复现轨迹。
- 故意绕过受管入口建立反例。如果模型无法识别隐藏共享状态，应限制保证范围或增加强制机制，不能声称已覆盖所有代码路径。
- 永久等待与事件循环阻塞由外部测试控制器超时终止；资源耗尽实验只有在独立受限环境中开展，不直接施加到开发宿主。

## 6. 最需要提前澄清的边界

### 6.1 “停止成功”的语义

至少区分四件事：关闭新调用入口、处理在途工作、回收本地资源、确认外部操作结果。具体完成条件取决于协议；超时只能证明没有在期限内完成，不能证明任务已经停止。

撤销一个本地句柄也不等于远端旧请求无法继续写入。若要承诺过时代次的写入被拒绝，需要实际执行操作的入口或接收端检查相应凭据，并把这个前提纳入适配器契约。

### 6.2 “隔离”的语义

分别声明异常传播、事件循环阻塞、内存、进程退出、共享资源和外部权限的边界。Worker 是可研究的适配方式，但不能直接等同于完整进程或内存隔离：Node.js 文档明确说明 Worker 可共享内存，且 `resourceLimits` 不能避免所有进程级 OOM。[Node.js Worker 文档](https://nodejs.org/api/worker_threads.html#new-workerfilename-options)

这意味着产品中的“隔离等级”应是一组具体验证过的性质，而非一个未经展开的开关。

### 6.3 “外部副作用受管”的语义

登记 intent、外部提交、本地获知结果是不同事件。适配器需要描述结果不确定时怎样查询、去重或处理；补偿完成还需要对应业务条件的验证。能力不足的接收端不能仅凭本地账本获得更强保证。

### 6.4 “自动识别完整”的语义

开发者声明、静态推断、运行观测、运行强制与外部对账应分别保留来源和覆盖范围。运行观测能为发生过的路径提供证据；对未观察到的路径，完整性仍需要额外约束或证明。

因此自动识别暂作为降低声明成本、发现模型遗漏的工具，首轮使用显式声明构造可检查的基线。

## 7. 准备工作的交付顺序

1. **核心语义规范 v0.1。** 明确三个契约、合法状态、服务模式、故障假设、保证前提和反例；用具体事件轨迹消除歧义。
2. **E1—E3 实验夹具。** 建立独立观察器、手工管理基线和候选协议实现。可优先用 TypeScript/Cordis 快照探索，以复用现有上下文；实验语言不决定最终产品语言。
3. **核心可行性记录。** 逐条写清哪些性质成立、依赖什么、在哪个反例上失败，以及代码、声明和运行开销。
4. **产品结构决策。** 根据结果选择 Cordis 适配层、独立运行时或协议与工具套件。新增原语和模块需要对应已观察到的需求。
5. **增强能力实验。** 用 E4—E6 决定隔离、外部 effect 和数据库管理的下一步范围；有状态迁移与热更新再单独设计实验。

阶段完成标准：每个准备对外承诺的核心性质都有明确前提、独立判据和可复现结果。失败可以推动修改协议或缩小承诺；没有执行的实验继续标为未知。

## 8. 留待下一步确定的选择

| 选择 | 当前建议 | 决策依据 |
|---|---|---|
| 第一个完整使用场景 | 选择一个真实存在局部启停、可选能力和资源管理问题的小型应用 | 能否用实际业务展示持续服务的收益 |
| 接入方式 | 先接受显式组件与 effect 声明 | 能否以可接受的改造成本获得可信保证 |
| Cordis 的角色 | 参考实现和候选适配目标 | E1—E3 能否复用其语义，额外包装成本多大 |
| 持久化范围 | 首轮核心允许仅在内存中运行；外部恢复实验单独引入持久记录 | 承诺的故障恢复范围是否要求跨进程存续 |
| 原语数量 | 暂不固定 | 每个概念能否由其他协议自然表达，删除后会丢失什么保证 |
| 框架、库或管理套件 | 暂保留选择 | 首个场景的接入方式与实验结果 |

本稿形成的是研究起点。当前已完成历史材料衔接、指定源码核对和验证设计；技术可行性需要后续实验给出结论。
