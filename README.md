# Continuum

面向持续服务（Continuous Service）的组件运行时与开发工具探索。

Continuum 希望让软件系统中的组件具有清晰的生命周期、依赖和作用边界，使系统在局部组件失效、停用或恢复时，仍能提供其余合法的服务能力。

项目目前处于**概念整理与技术可行性验证的准备阶段**。本文描述的是研究方向和设计目标，尚未提供可使用的运行时、稳定 API 或安装包。

## 为什么研究持续服务

一个应用可以包含许多分别成立的能力：数据处理、查询、通知、扩展插件，以及各种后台任务。它们可能具有不同的依赖、资源需求和恢复方式。

例如，通知组件暂时不可用时，独立的查询服务应能继续工作；可选的数据增强能力缺失时，处理服务可以进入事先定义的基础模式；依赖恢复后，受影响的组件应能局部恢复。

要实现这样的行为，需要能够回答：

- 一个组件提供什么，当前实际依赖谁？
- 它拥有哪些资源、任务、状态和副作用？
- 它停止或失败时，哪些能力必须受到影响？
- 什么条件允许它重新激活，怎样确认恢复已经完成？

Continuum 希望将这些问题转化为明确、可组合、可验证的运行时协议。

## 这里的“持续服务”是什么

本项目采用以下工作定义：

> 在声明的故障模型、资源耦合与服务策略下，系统能够限制局部扰动的影响，持续提供仍然合法的服务模式，并在条件稳定后完成可解释的局部恢复。

这一概念主要关注三个方面：

1. **影响遏制**：组件变化或失效的影响具有可描述、可验证的边界。
2. **部分有效性**：系统能够表达完整服务、合法降级和局部不可用。
3. **局部恢复**：依赖与资源条件恢复后，相关组件能够重新收敛到有效状态。

热替换、动态配置和在线演进是这一基础能力的应用场景。有状态恢复、一致切换和更强的故障隔离，需要各自的协议与验证。

服务连续性的保证取决于具体实现及其前提：组件的逻辑边界需要与实际故障域对应；资源释放、任务取消和外部业务补偿也需要分别定义。

## 拟探索的产品结构

Continuum 倾向于以一个小型、可嵌入的运行时为基础，逐步扩展可选能力：

| 层次 | 探索方向 |
|---|---|
| 运行时内核 | 组件身份与生命周期、能力提供与依赖绑定、资源和副作用所有权、局部协调与恢复 |
| 适配器 | Web、事件、数据库、消息、状态恢复，以及不同执行环境和隔离方式 |
| 管理与开发工具 | 持久化管理、影响分析、副作用记录与对账、自动识别、可观测性和 CI/CD 验证 |

设计上希望支持渐进接入：小型应用能够使用嵌入式核心，有治理需求时再引入持久管理和开发工具。具体的实现语言、公开 API、模块划分和部署方式将由验证结果决定。

## 当前重点

准备工作围绕三个候选契约展开：

- **组件契约（Component Contract）**：身份、生命周期、能力依赖、服务模式与恢复边界。
- **作用契约（Effect Contract）**：资源与副作用的所有权、释放方式、外部可见性及结果证据。
- **转换契约（Transition Contract）**：激活、停用和恢复的前提、执行过程、完成条件与失败分支。

近期将先明确核心语义，再通过小型实验验证依赖变化、部分初始化失败、重复启停、资源清理和迟到异步任务等场景。随后再研究故障隔离、外部操作的不确定结果，以及可选持久管理能力。

每项对外保证都应对应明确的适用条件、独立的观察判据和可复现的实验结果。

## 研究起点

本项目的讨论起于 [Cordis](https://github.com/cordiverse/cordis) 的组件生命周期与组合模型，并进一步延伸到状态管理、数据库机制、故障恢复和外部副作用管理。

目前将 Cordis 作为重要的研究参考与候选适配目标。持续服务的概念、实现方式和产品边界仍在探索中。
