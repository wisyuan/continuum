# Continuum

面向持续服务（Continuous Service）的组件管理与执行协调项目。

Continuum 希望让软件系统中的组件具有清晰的生命周期、依赖和作用边界，使系统在局部组件失效、停用或恢复时，仍能提供其余合法的服务能力。

项目目前处于**概念整理与技术可行性验证的准备阶段**，已形成第一版设计基线。本文描述设计目标；实验尚未执行，仓库尚未提供可使用的运行时、稳定 API 或安装包。

## 为什么研究持续服务

一个应用可以包含许多分别成立的能力：数据处理、查询、通知、扩展插件，以及各种后台任务。它们可能具有不同的依赖、资源需求和恢复方式。

例如，通知组件暂时不可用时，独立的查询服务应能继续工作；可选的数据增强能力缺失时，处理服务可以进入事先定义的基础模式；依赖恢复后，受影响的组件应能局部恢复。

要实现这样的行为，需要能够回答：

- 一个组件提供什么，当前实际依赖谁？
- 它拥有哪些资源、任务、状态和副作用？
- 它停止或失败时，哪些能力必须受到影响？
- 什么条件允许它重新激活，怎样确认恢复已经完成？

Continuum 希望将这些问题转化为明确、可组合、可验证的运行时协议。

## 这里的“持续服务”是什么

本项目采用以下工作定义：

> 在声明的故障模型、资源耦合与服务策略下，系统能够限制局部扰动的影响，持续提供仍然合法的服务模式，并在条件稳定后完成可解释的局部恢复。

这一概念主要关注三个方面：

1. **影响遏制**：组件变化或失效的影响具有可描述、可验证的边界。
2. **部分有效性**：系统能够表达完整服务、合法降级和局部不可用。
3. **局部恢复**：依赖与资源条件恢复后，相关组件能够重新收敛到有效状态。

热替换、动态配置和在线演进是这一基础能力的应用场景。有状态恢复、一致切换和更强的故障隔离，需要各自的协议与验证。

服务连续性的保证取决于具体实现及其前提：组件的逻辑边界需要与实际故障域对应；资源释放、任务取消和外部业务补偿也需要分别定义。

## 设计基线

Continuum 以 [Cordis](https://github.com/cordiverse/cordis) 为首个执行适配目标，将其服务、运行单元、依赖与副作用管理思想映射到真实系统环境，并保持独立的管理模型。

- **明确托管边界。** 普通对象由业务代码自由创建和使用；框架协调受管单元的激活、撤销与恢复。同一服务中的非受管部分，需要明确其与持续服务保证的关系。
- **保留 Service 与 Fiber 的区别。** 服务能力、具体运行单元、提供与消费关系、资源归属分别表达。
- **以注册契约接入程序。** 开发者或维护人员声明依赖、行为阶段、清理逻辑和恢复条件；黑盒程序可以通过显式标记与适配器接入。
- **统一受管副作用与观察记录。** 默认记录生命周期及监听器、定时器、连接、订阅等受管副作用，关联部件日志与监控。业务操作按需显式纳入。

## 管理架构

数据库承担大规模组件时空依赖图的存储、管理与相关查询计算，使系统能够按需处理相关子图，突破单机同时持有全图的限制。具体能力仍需实验验证。

| 部分 | 设计职责 |
|---|---|
| 全局图管理服务与数据库 | 管理期望配置、实际状态、服务绑定和资源关系，支持影响分析、约束检查与操作规划 |
| 执行节点与适配器 | 按需取得子图与约束，驱动受管生命周期，核验真实资源并报告结果 |
| 本地记录与可观测性 | 保存关键管理记录、异步同步、实施背压，并关联日志、指标与运行状态 |
| 可接入调度模块 | 根据容量和位置提出部署安排，由核心检查相关约束并协调执行 |

数据库后端可替换，首版先实现一个后端。服务绑定和依赖结构的主动变更，默认经全局图管理确认后再发布生效；暂时失联时，执行节点可以在已确认的局部规则下处理本地可判定的故障、撤销与清理。

## 恢复与阶段边界

对能够控制执行入口、且纳入跨重启恢复保证的外部副作用，采用“持久化操作意图 → 执行 → 登记结果”的协议。结果不明时，由适配器按注册契约核验。清理失败后继续保留资源约束的策略，由契约明确启用。

关键记录使用本地持久化缓冲，再异步同步管理数据库。缓冲容量不足时限制需要新增记录的操作，并为已有操作的结果、撤销和清理预留空间。

实验阶段验证执行进程退出与重启后的恢复。整机意外断电后的恢复保证留到正式产品化；永久挂起、死循环的感知与强制处置属于后续扩展。

## 首轮验证

| 对象 | 要回答的问题 |
|---|---|
| 真实业务链 | 数据库连接、消息订阅和后台任务能否完成登记、局部失效、清理、进程重启核验与恢复 |
| 大规模合成依赖图 | 数据库能否承担相关图查询、计算和变更管理，执行节点能否按需获取子图 |

首个真实资源实验可以使用一个 Cordis 宿主。正式产品的部署形态、具体生产服务、公开 API 和实现语言仍需独立设计。数据库选型、规模与性能指标，以及跨节点协调协议，是下一步的待验证项。

每项对外保证都应对应明确的适用条件、独立的观察判据和可复现的实验结果。
